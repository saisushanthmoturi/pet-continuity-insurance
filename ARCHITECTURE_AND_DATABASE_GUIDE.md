# Pet Continuity Insurance Microservices Architecture & Database Guide

## 1. Context of the Architecture & System Evolution

### Background & Initial Problem
- **API Gateway Complexity**: The API Gateway previously included `spring-boot-starter-security`, creating conflicts between reactive routing (`RouteLocator`), CORS preflight handling, and proxy header forwarding.
- **Service-Level Security Inconsistencies**: Method-level authorization (`@PreAuthorize`) was uneven across microservices, and token claims weren't uniformly forwarded from the gateway.
- **Database Schema Gaps**: The microservices required a comprehensive 24+ table domain architecture across 8 standalone databases (`auth_db`, `customer_db`, `pet_db`, `underwriting_db`, `policy_db`, `claims_db`, `payment_fund_db`, `care_verification_db`), with fully automated timestamps (`created_at`, `updated_at`, etc.).

### Completed Architecture Upgrades
1. **API Gateway Decoupling**:
   - `spring-boot-starter-security` was completely removed from `ApiGateway/pom.xml`.
   - Obsolete `SecurityConfig.java` in the gateway was removed.
   - Converted into a high-performance, non-blocking reverse proxy with a Spring Cloud Gateway `GlobalFilter` (`JwtAuthenticationFilter.java` at `order = -100`).
   - Bypasses public endpoints (`/api/auth/**`, `/fallback/**`, `/actuator/**`).
   - Parses the JWT from either an HttpOnly Cookie (`jwt_token`) or `Authorization: Bearer <token>`, validates the signature in memory via `JwtUtil.java`, and injects headers downstream:
     - `X-User-Id`
     - `X-User-Role`
     - `X-User-Email`
2. **Downstream Microservice Security**:
   - Each downstream service uses reactive Spring Security (`@EnableReactiveMethodSecurity` and `ReactiveSecurityConfig`).
   - Method-level authorization is enforced via `@PreAuthorize("hasAnyAuthority('ROLE_CUSTOMER', 'ROLE_ADMIN', ...)")`.
3. **Database Domain Architecture & Autogenerated Timestamps**:
   - Master schema and seed script created in `database_seed_data.txt`.
   - All audit timestamps (`created_at`, `updated_at`, `assessed_at`, `submitted_at`, `payment_date`) have `DEFAULT CURRENT_TIMESTAMP` and `ON UPDATE CURRENT_TIMESTAMP` in MySQL DDL and `LocalDateTime.now()` defaults in Java entities.
   - Complete entities and reactive repositories were created/updated across all 8 microservices.
4. **Git Synchronization**:
   - All 10 backend projects compile cleanly (`BUILD SUCCESS`).
   - All changes were committed and pushed to the **`backend`** git branch.

## 3. Databases Used, Table Definitions & Attributes

### 1. `auth_db` (Auth Service)
* **`users`**:
  * `user_id` (BIGINT, PK, AUTO_INCREMENT)
  * `username` (VARCHAR(100), NOT NULL, UNIQUE)
  * `email` (VARCHAR(150), NOT NULL, UNIQUE)
  * `password_hash` (VARCHAR(255), NOT NULL)
  * `role` (VARCHAR(50), NOT NULL)
  * `status` (VARCHAR(50), DEFAULT 'ACTIVE')
  * `created_at` (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
  * `updated_at` (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP)
  * `last_login_at` (TIMESTAMP)
* **`refresh_tokens`**:
  * `token_id` (BIGINT, PK, AUTO_INCREMENT)
  * `user_id` (BIGINT, NOT NULL, FK -> users.user_id)
  * `token` (VARCHAR(500), NOT NULL, UNIQUE)
  * `expires_at` (TIMESTAMP, NOT NULL)
  * `status` (VARCHAR(50), DEFAULT 'ACTIVE')
  * `created_at` (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
